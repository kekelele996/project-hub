# GitHub 多仓库灾备

管理员在「GitHub 灾备」维护多个 GitHub 账号，以及每个工程对应的多个私有仓库。每个工程版本单独保存 ZIP、启动截图、功能截图与校验清单；工程版本、项目范围和领取记录不因备份或恢复而变化。

## 配置主密钥

后端使用 AES-256-GCM 加密 GitHub Token，随机 nonce，账号 ID 作为附加认证数据。页面和查询接口仅显示 Token 尾号，不返回明文或密文；审计日志不记录 Token。

在 `.env` 中配置 `BACKUP_MASTER_KEY`，内容为 32 字节随机数的标准 Base64 编码。可用以下命令生成：

```sh
openssl rand -base64 32
```

主密钥为空时，既有工程台功能继续运行，灾备配置关闭；格式错误会阻止后端启动。修改配置后重建或重启 API：

```sh
docker compose up -d --build api web
```

主密钥要另存于受控的密码管理器或密钥备份中，数据库备份不包含它。不要随意更换：更换或遗失会导致已有 Token 无法解密，需要重新录入。密钥不参与 ZIP 加密，仓库中的版本文件仍可由拥有仓库权限的 GitHub 用户访问。

## 工程池上传时自动建仓

灾备账号是全局配置。在「GitHub 灾备 → GitHub 账号」配置并启用账号后，工程池上传自动备份到全部已启用、已验证且未到期的账号，无需每个工程选择账号、绑定仓库或手动同步。上传新工程时可指定仓库短名，默认为 `engineering`；追加版本沿用原名。

命名规则为 `ph-<仓库短名>-<工程ID去除连字符>`。短名为 3～48 位小写英文字母、数字和单个连字符，首尾必须为字母或数字，禁止连续连字符。例如 `elderly-care` 会生成 `ph-elderly-care-50d63ebffe9e42509ae4810803079af3`。同名工程依靠各自 ID 区分；工程改名不改仓库名。每个灾备账号的真实 GitHub login 为各自仓库所有者，各账号仓库同名。

上传成功会在同一个数据库事务中保存工程版本和自动同步目标。代码分析完成后，后台创建带初始 README 的私有仓库，然后上传 ZIP、截图和校验清单到版本专属 Release。每次追加版本沿用原仓库、建立新 Release，历史备份保留。上传完成不等于灾备完成；在「GitHub 灾备 → 同步记录」看到 `ready` 才表示远端文件逐个校验成功。建仓或上传失败不撤销本地版本，按现有重试入口重新执行；已有仓库仅在归属标记与工程匹配时复用，避免误写其他仓库。

建议使用具有 `repo` 权限的 classic PAT 实现私有建仓和后续 Release 上传。细粒度 Token 需要支持创建及访问新仓库，并有 `Contents` 读写权限；仅授权已有仓库的 Token 不适合此流程。账号录入验证仅校验身份，无法证明未来新仓库的写入权限。

后台自动补齐已有未归档工程的所有已分析完成版本；新增并启用灾备账号后，也会自动为这些工程建立该账号副本。历史工程未设置短名时使用 `engineering`。停用账号、停用目标或关闭目标自动同步会阻止后续同步，后台不会自动重新启用这些配置。已有手动绑定的仓库可以继续使用。

API 上传仅需可选的 `backup_repo_name`，返回 `backup_targets:[{id,repository_url}]` 和 `backup_status`；按 `engineering_id` 查询任务覆盖全部副本。省略仓库名也会自动备份，新工程默认 `engineering`，追加版本沿用原名；托管仓库绑定后传不同短名返回 409。旧 `backup_account_id` 仅校验账号有效性，不限制全局同步账号，推荐省略。旧响应字段 `backup_target_id`、`backup_repository_url` 对应首个目标。

若未配置密钥或暂无可用账号，API 本地上传仍可完成，但明确返回 `backup_status=unconfigured`、`backup_targets=[]`，配置就绪后后台补齐。工程池页面要求至少一个可用全局灾备账号；每次上传无需重复配置。

工程池上传使用 ZIP 的版本快照备份；不会自动推送源码分支、Git 历史或 LFS。

## 批量工程浏览

备份仓库每页只加载20条。「同步记录」按工程收纳全部账号的备份，默认折叠，每页20个工程。工程行显示账号数、仓库数、版本数、记录数、各状态数量和最近记录时间；同一版本在多个账号备份只计一个版本。点击工程名前的箭头展开，每次只展开一个工程，按需加载每页10个版本，新版在前。同一版本的多个账号共用版本栏，每个账号分别显示仓库、状态与重试、恢复、Release 和详情操作。同一版本的账号记录不会拆到不同页。

可以搜索工程名称或仓库，筛选仓库启用状态，或按任务状态与同步/恢复类型筛选；仓库摘要与展开记录均应用当前筛选，版本数按不同版本ID计数。页码输入允许直接跳到指定页。长仓库名在列表中省略显示，悬停显示完整名称，任务详情保留完整地址和错误信息。

当前页存在处理中任务时每2～2.5秒刷新；完成页每30秒刷新，后台标签页暂停自动刷新。工程上传表单只显示全局可用账号数量，不展开全部账号。后台每30秒最多扫描100个待补齐工程和100个待补齐版本，扫描与文件上传分别运行，不会因长上传停止补齐。单实例上传仍按队列串行执行，工程规模不等于可同时完成的上传数量，耗时取决于文件大小和 GitHub 限流。

## 手动绑定已有仓库

1. 在 GitHub 为账号创建 Personal Access Token。建议使用细粒度 Token，仅授权需要备份的仓库，仓库 `Contents` 权限设为读写，`Metadata` 为只读。Token 必须能读取账号信息与目标私有仓库，并创建 Release、上传和下载资产。
2. 事先创建私有仓库，初始化默认分支，例如勾选创建 README。此入口仅绑定已有仓库；自动建仓请使用工程池上传表单。
3. 在「GitHub 账号」录入名称、Token 和可选到期时间。保存时验证 GitHub 账号；后续可重新验证、替换 Token、修改到期时间或停用。
4. 在「备份仓库」选择工程和账号，填写仓库所有者及仓库名称。保存前验证仓库私有状态、写权限和默认分支。
5. 开启自动同步或执行手动同步。自动同步为已分析完成的版本建立任务；任务状态及重试入口位于「同步记录」。

到期时间是管理员录入的本地期限，并非平台自动推断 GitHub Token 的实际期限。GitHub 提前撤销或过期会在验证、同步时显示错误。

账号停用、到期或仓库目标停用会阻止后续任务。已经发往 GitHub 的请求可能完成；任务最终提交前会再次检查当前账号与目标状态。停用不会删除远端 Release 或历史记录。

## 副本格式和恢复

工程版本以专属 Release 保存。版本标识包含工程与版本 ID，资产包含 ZIP、截图和清单，平台不会覆盖其他人的 Release。重复同步复用内容一致的资产，内容冲突会失败并保留错误信息。

同步完成前会校验远端文件 SHA-256。只有校验完成的任务显示成功；失败可以手动重试。同步记录保留远端 Release 地址和校验结果，管理员可以在 GitHub 检查实际副本。

恢复选择已成功的同步记录，下载并校验 ZIP、截图与清单。验证通过后恢复到当前版本的本地文件路径；不会改变版本 ID、分析统计或已有领取。恢复任务也有独立状态与审计记录。

这里备份的是 ZIP 代码快照及截图，不包含原始 Git 提交历史、分支与 Git LFS 对象。Release 所指向的仓库提交用于定位备份仓库，不代表上传工程源码的原始 commit。

GitHub 多仓库副本不能代替数据库备份。用户、项目、领取、版本元数据和 Token 密文仍需要按照 [运行与备份说明](operations.md) 单独备份 PostgreSQL，主密钥另存。数据库丢失时，应先恢复数据库，再使用相应记录恢复本地资产。

## 验证范围

自动测试使用本机模拟 GitHub HTTP 服务与真实 PostgreSQL，验证加密、权限、私有仓库检查、Release 上传、校验、重试和恢复。浏览器验收不会使用机器上的 GitHub CLI 凭证创建或修改外部仓库。实际远端同步需要管理员在平台录入自己的 Token 和目标仓库后触发。

可用测试专用 helper 复现浏览器流程。在 `backend` 目录启动下列命令，连接字符串必须指向测试数据库：

```sh
TEST_DATABASE_URL="$PROJECT_HUB_TEST_DATABASE_URL" \
BACKUP_BROWSER_DEMO=1 \
go test ./internal/app -run '^TestBackupBrowserDemo$' -count=1 -v -timeout=0
```

helper 默认只监听 `127.0.0.1:8080`，输出测试登录信息和本机 mock 地址；前端按正常 Vite 开发方式运行。`archive` 仓库成功同步，`flaky` 首次上传失败后可重试；第二个模拟账号 Token 为 `ghp_local_fake_9012`。结束时发送 SIGINT 或 SIGTERM，会清理临时 schema 与文件。生产入口不会接受自定义 GitHub API 地址。
